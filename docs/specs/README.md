# Specification index

The Hermes-style experiential-learning MVP remains the only accepted product implementation. A Codex integration, a plugin tracing facility, and a Hermes-derived prompt-stack revision are proposed separately, while an open question raised by the wake harness is carried as a finding; none changes the accepted Claude MVP:

- [Spec-0001: Hook-driven experiential learning plugin MVP](0001-hermes-style-experiential-learning-mvp.md) — **Accepted; implemented.** The whole offline suite and nine of ten packaged smoke checks observed passing. The tenth, the asynchronous wake, is evidenced by the [Spec-0002](0002-pty-wake-harness.md) harness.
- [Spec-0002: Automated verification of the asynchronous wake](0002-pty-wake-harness.md) — **Implemented; verified except its section 6.1.** Test tooling only. The harness runs behind `make wake`; its model-free self-checks, its harness self-checks (`make test-harness`), and both live checks were observed passing together (2026-08-01), and `make wake-repeat` then completed ten consecutive runs with no failure (2026-08-02). Criteria 6.2 to 6.5 have been observed. 6.1 asks for a detected wake in ten consecutive runs and nine of the ten reached that assertion: five of the twenty checks skipped, having no candidate staged to watch for, and one of the five was a wake check.
- [Spec-0003: Codex integration for experiential learning](0003-codex-integration.md) — **Proposed; integration analysis only.** Maps every current Claude-specific seam to Codex, defines a dual-host adapter design, and records missing async wake, command-expansion provenance, generic tool-failure, strict no-tools, and path-scoped behavioral-rule parity. No Codex implementation or acceptance result has been observed.
- [Spec-0004: Plugin execution tracing](0004-plugin-execution-tracing.md) — **Proposed; not implemented.** An opt-in trace inside the plugin recording what each hook decided and why, with the evidence bundle kept as a keyed *shape* rather than its content, so two live runs can be compared mechanically. Written to make [Spec-0005](0005-reviewer-decline-asymmetry.md) measurable; it does not claim to explain it, and its section 13 keeps the slices aimed at that question behind a named hypothesis. Off by default, and its acceptance gate is that the default path stores nothing the privacy rules forbid.
- [Spec-0005: The reviewer declines far more often on the negative control](0005-reviewer-decline-asymmetry.md) — **Open question; no mechanism identified.** Not a design. It carries one measured behaviour that [Spec-0002](0002-pty-wake-harness.md)'s runs produced while establishing something else: the negative control's review has declined seven times against the wake check's once, on an identically scripted exchange. Spec-0002 records none of it and closed on its own criteria. Records the two hypotheses already eliminated, why offline replay does not reproduce it, and what closing it would look like — including deciding it is not worth the model usage.
- [Spec-0006: Hermes-derived prompt stack adoption](0006-hermes-prompt-stack-adoption.md) — **Proposed; research and design only.** Adapts Hermes's active correction handling, fact/procedure split, owner-first routing, class-level name veto, and negative-learning rules to the MVP's no-tools reviewer and explicit-approval mutator. It also records that the current `improve` skill advertises support-file routing the allowlist cannot stage, defers that wider mutation surface, and requires both opt-in model evaluation and packaged live evidence before the prompt can be called improved.

Statuses here follow the evidence rule in [`AGENTS.md`](../../AGENTS.md#specification-status): nothing is marked done before a command has been run and its result read.

The previous architecture and phase specifications have been moved unchanged into [`docs/hypothetical-extensions/specs/`](../hypothetical-extensions/specs/README.md). They are research material for possible later extensions, not accepted requirements, dependencies, or release gates for the MVP.
